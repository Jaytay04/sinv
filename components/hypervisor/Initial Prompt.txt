# Role
You are a Senior Systems Architect and Kernel Developer specializing in x86_64 virtualization, Windows Driver Frameworks (WDF/WDK), and Memory Management Units (MMU). Your goal is to architect and implement the core engine of a **Type 2 Hypervisor** designed for **advanced memory debugging and dynamic analysis** of 64-bit Windows applications on **Windows 11**.

# Project Objective
Create a modular, low-level hypervisor that sits between the Ring 0 Kernel (Windows 11) and Ring -1 (The Hypervisor) to intercept and modify memory, control registers (CR3), and handle VM-Exits efficiently. The primary use case is **bypassing Ring-0 memory protection mechanisms** (e.g., shadow stacks, page protection changes) to allow read/write access to protected memory regions of a target application for debugging purposes.

# Technical Constraints & Environment
1. **OS**: Windows 11 (Build 22000+)
2. **Architecture**: x86_64 (64-bit)
3. **Virtualization Tech**: Intel VT-x / AMD-V (focus on Intel EPT for memory translation).
4. **Language**: C/C++ (C11/C++17) with inline Assembly where necessary.
5. **Driver Model**: WDK (Windows Driver Kit) KMDF.
6. **Build System**: **Strictly CMake**. No Visual Studio `.vcxproj` files unless generated by CMake. The build command should be `cmake -B build` and `cmake --build build`.
7. **Target Context**: The target application uses advanced kernel-level memory protections similar to modern anti-tamper systems. Assume the target resides in Ring 0 and uses features like:
 - Page Protection Changes (Read-Only/Execute-Only pages).
 - Shadow Stack (Intel CET) for return address verification.
 - Periodic memory scans (CR3 walking).

# Required Components to Implement

## 1. The Host Driver (Ring 0)
- Create a minimal Kernel Mode Driver (`.sys`) that:
 - Enumerates CPU cores using `KeGetLogicalProcessorInformation`.
 - Executes the `VMMCALL` instruction to switch each core into the Hypervisor (Ring -1).
 - Handles the transition from Long Mode to Long Mode Root (VMX Root) Operation.
 - Provides an IOCTL interface for the User-Mode Controller to load/unload the hypervisor.

## 2. The Hypervisor Engine (Ring -1)
- **Initialization**:
 - Clear the VMCS (Virtual Machine Control Structure) and set up `VMCS` region.
 - Configure `VMXON` and `VMCS` regions with proper page alignment.
 - Handle `VMPTRST` and `VMPTRLD`.
- **VM-Exit Handlers**:
 - Implement a generic `VM-Exit` handler.
 - Specifically handle:
 - `CPUID`: To maintain transparency to the guest OS (e.g., masking the `HYPERVISOR` bit in `EAX` of `CPUID(1)`).
 - `CR3 Write`: To intercept page table switches (crucial for memory scanning).
 - `EPT Violation`: To handle memory access when the target application reads/writes to protected pages.
 - `HLT`: To return control to the guest efficiently.
 - `VMMCALL`: For communication between the Guest Kernel and the Hypervisor.
- **Memory Management (EPT - Extended Page Tables)**:
 - Implement a simple EPT walker.
 - Create a function to hook specific physical addresses by modifying EPT PTEs (Page Table Entries).
 - **Key Feature**: Allow changing the "Write-Through" and "Cache Disable" bits, and most importantly, the **Access Rights** (Read/Write/Execute) of specific pages in the target process. This allows the application to write to "Read-Only" pages without triggering Page Faults in Ring 0.

## 3. Transparency and Stability Strategies
- **Hiding the Hypervisor**:
 - Mask `CPUID` leaf 1, bit 31 (Hyper-V present bit).
 - Mask `MSR` `0x40000000` (Hypervisor Vendor String).
 - Ensure `RDTSC` behaves naturally to minimize timing discrepancies.
- **Timing Optimization**:
 - Minimize VM-Exit latency by using a fast-path handler for common exits.
